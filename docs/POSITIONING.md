# Why Parallax

**Parallax turns an outcome into a reviewed, checked project patch using the coding agents you already use, from the Codex conversation you are already in.**

It is for developers who want to delegate a bounded feature or repair, mix providers deliberately, and return to one result with evidence. Their project often already has staged work, unfinished edits and untracked files. They should be able to choose a team without becoming its full-time scheduler or moving into another IDE.

## The product promise

The unit of work is an outcome with acceptance criteria. The unit of delivery is a patch with a verification record. Workers implement in private snapshots; a different provider reviews their changes; the runtime checks the combined candidate before application. Failed reviews and checks become repair work with a retained history. The runtime preserves the developer's staging and unrelated edits, or stops with the work available for inspection.

Model choice matters because a second perspective can expose a concrete error. It is a choice, not a guarantee that more agents outperform one. Parallax defaults to quality and records requested and effective settings so the team can be reproduced deliberately. CLI subscriptions and API connections can coexist; custom compatible models have an explicit capability catalog.

The task graph answers practical questions: What is blocked? Which attempt failed? Who reviewed the replacement? What is ready to integrate? It leads into the diff, recorded check output and verification gates. The graph does not expose private reasoning or promise that a visually complete plan is correct.

## What makes this a focused product

The differentiator is the complete local delivery workflow: Codex-native invocation, a mixed-provider team, independent review and repair, integration into the effective dirty working tree, and a portable evidence record. Each part supports that one job. This is a product focus and implementation contract, not a claim that no competitor offers a similar feature.

Current products already do substantial work in this space. [Superset](https://docs.superset.sh/overview) provides parallel CLI agents, isolated workspaces, diff review, and several interfaces. [Conductor](https://www.conductor.build/docs/concepts/git-worktrees) builds agent workflows around worktrees with commands and review flows. [OpenHands](https://www.openhands.dev/blog/20260506-the-verification-stack) documents automated verification, code review, functional QA and repair loops. Orchestration, worktrees and verification alone are not novel claims.

Parallax should earn preference from developers who want this specific workflow inside Codex, with their existing sign-ins, explicit provider capabilities, no new hosted orchestration account, and careful integration into ongoing local work. Broad fleet management, a complete IDE, remote execution, team governance and hosted automation are different jobs. Version 1.0 does not pretend to cover them.

## Evidence and launch standard

The recorded four-provider acceptance build starts from failing code. Codex coordinates, Claude and Antigravity implement, Grok rejects an incomplete implementation and reviews the repaired candidate. The unchanged acceptance command finishes with eight passing tests. The final patch changes two files. Failed attempts and disagreements remain inspectable. This establishes that the delivery path works on that fixture; it is not a benchmark or proof of market demand.

Release validation also covers dirty-worktree preservation, concurrent edits, failed-check gates, permission denials, provider-specific resume, malformed streams, cancellation, recovery and duplicate-action prevention. Studio is checked on desktop and mobile, with keyboard interaction, light mode and reduced motion. API protocols are tested against deterministic endpoints; live API inference requires real account credentials and is reported separately.

The next market test is whether developers complete useful tasks repeatedly with less coordination effort. Observe first-run setup success, useful patches delivered, repair and check rejection rates, time spent intervening, unintended file changes, and repeat use. Compare against a single-agent baseline on the same tasks before making productivity or quality claims. “Premium” should mean clear controls, predictable behavior and evidence users can trust, in addition to polished visuals.

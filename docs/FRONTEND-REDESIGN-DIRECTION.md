# Parallax visual direction and staged build

Round 2, October 11, 2026. User direction: a polished, distinctive developer product; improve visual identity, navigation and excess information. This follows the researched brief and uses the installed Anthropic frontend-design skill.

## Brief before code

The memorable element should be the change being inspected. The website explains a task/result clearly and makes available installation and account entry visible. Studio organizes the same work around tasks, repositories, human review and delivery. Execution remains on explicitly selected user-owned machines; the interface must name that scope without becoming a dashboard of infrastructure.

Two independently designed concepts will compare different compositions, each with a matched task view and a blocked state. Plans must specify four to six core colors, deliberate type roles and an ASCII layout before code. Screenshots and an independent critique determine which composition becomes the first implemented slice. No customer preference or conversion improvement is claimed from this internal review.

## Critique of round 1

The first board established useful hierarchy but still used familiar dark/warm-accent styling, repeated labels and large bordered examples. Those were draft choices, not user-selected requirements. The frontend-design skill makes their generic quality explicit. Keep the research's result-led story and simple navigation; revise the visual treatment and use type, alignment and one domain-specific composition to carry the identity.

Remove redundant eyebrows and ornamental numbering. Use numbering only for an actual sequence. Avoid identical feature cards and a wall of setup caveats. Preserve short availability, privacy and evidence explanations at the relevant choices, with clear access to details.

## Selection criteria

| Criterion | What the concept must demonstrate |
| --- | --- |
| Product comprehension | A visitor can identify the reviewed patch, the separate human decision and the available installation path. |
| Visual specificity | The central composition comes from coding changes and independent perspectives; it does not rely on a generic orb, gradient or card kit. |
| Hierarchy | One primary acquisition action, visible account access and an intelligible task next action. Main work precedes diagnostics. |
| Working readability | Comfortable body text, readable diffs, concise status and clear labels; metadata does not compete with the work. |
| System coherence | Website and Studio share type, spacing, control rules and identity while accommodating different reading and working contexts. |
| Responsive behavior | Named scope and discoverable navigation on mobile; bounded code scrolling, no page overflow or covered actions. |
| Honest states | Public 1.3 versus supplied preview 1.4; unpublished Mac installer; simulated examples; unknown costs; current/historical evidence; blocked actions with remedies. |

## Implementation after critique

Build in separate reviewable slices: public shell/result story and installation; Studio navigation/repositories; compact task/review layout and actionable delivery status. Reuse authentication, path permissions, immutable evidence and operation contracts. A clearer repository entry must use actual approved paths and separately authorized GitHub delivery; cloning is not implemented by a visual control.

Validate a slice before broadening it. Use real browser inspection at desktop and 390/320px, keyboard/focus and reduced motion, plus the existing functional suites. Preserve legacy entry points and advanced run/graph/evidence access. Do not introduce account-gated local tools, newsletter signup, billing, automatic actions or a production deployment as a side effect.

Real customer task observation and live provider/account/GitHub acceptance remain distinct from visual and deterministic checks.

## Selected direction after browser comparison

The Perspective concept was inspected at 1440px and 390px alongside the graphite Control concept. Perspective is selected: its expanded Archivo promise and offset request/patch/finding object identify a second view of a specific code change. Control's single-task reading sequence is useful below the opening, but its centered graphite workbench is less distinctive as the product identity. This is an internal design judgment, not user-research evidence of conversion.

Production tokens: Daylight `#F8FAFF`, Ink `#18305D`, Slate `#5B6D87`, Plane `#E9EEF8`, Perspective blue `#345BE8`, Alert `#A64554`. Archivo carries headings, prose and controls; locally bundled Plex Mono carries code. New sessions default to light; saved dark preferences remain available. Code stays unrotated. The review annotation moves into normal flow on mobile after prototype critique found that an absolute note could cover the code and check footer.

Desktop public layout: named navigation, full-width two-line promise, concise purpose and installation action beside one patch object, then a staged workflow, bounded task examples, installation selector and practical details. Mobile: named Menu, account entry, readable promise/action, flat patch and review below it. The existing average-helper example now supplies both the opening patch and detailed walkthrough, avoiding two competing sample tasks. Modernization remains a runnable preview exercise.

Studio uses one labeled primary navigation and one contextual task queue. Current candidate/evidence/next action precede activity. Repositories use current approved worker folders with separate GitHub delivery bindings. Approval, local application and publication remain separate facts and actions. Advanced graph/run/evidence views and shortcuts remain available.

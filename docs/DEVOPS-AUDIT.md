### Final command-isolation review

A real macOS check with a private command environment could read a public synthetic key under `/private/var/tmp`, outside the former named user-data deny list. No real key was accessed. The new shared isolation policy registers live runtime/API state roots and the actual configured App key before its environment setting disappears. Both native command wrappers deny those paths; a candidate inside runtime state retains only its specific candidate grant. Whole-state and filesystem-root grants are refused. Keys inside a granted project are still masked, and symlink key targets are included.

The Linux wrapper no longer binds `/` read-only. Its empty root receives system code, selected public `/etc` configuration, selected toolchains, fresh `/proc` and `/dev`, and exact project/check-environment grants. Custom host mounts such as `/mnt`, `/data` and `/run/secrets` are absent except for explicit grants, with registered state/key masks applied independently of their locations. This does not promise confidentiality for files an operator places inside an exposed toolchain or system-code directory without registering them. macOS still exposes OS/runtime resources needed for native launch; unrelated custom non-user paths remain readable unless registered. Keep all product state registered and App keys outside approved projects.

## Persistence, backup and recovery procedure

The relay requires a persistent volume mounted at `/data`, one process and one replica. `railway.json` fixes the replica count at one, and the hosted entry point takes a process lock before opening the runtime. Neither configuration creates a Railway volume automatically. Confirm the volume attachment before enrollment; an HTTP health response alone does not prove persistence.

For a consistent backup, stop dispatch and active work deliberately, inspect durable workflow/publication status, then stop the runtime before snapshotting the full volume. Preserve all SQLite databases, WAL/SHM sidecars, workflow journals and artifacts together. Copying only `state.sqlite3` while the runtime is live is not a consistent whole-product backup. Keep the backup private and encrypted under the operator's storage controls, and record its source version and timestamp.

Worker candidates and project snapshots reside on each paired machine. A relay-volume backup does not recover a lost worker candidate. Back up the worker's Parallax state and managed candidate directories separately, alongside the operator's project backup policy. Provider sign-ins and GitHub App secrets have separate credential recovery procedures and must never enter a browser build or public support archive.

Test a restore on a disposable staging volume and worker, with no production credentials and publication disabled. Start one runtime against the restored state, confirm workspace isolation and expected operation records, then inspect original project fingerprints and remote publication state before retrying an interrupted action. Recovery must retain consumed execution budgets. Never delete a journal or manufacture a new request ID to bypass an uncertain publication.

Before enabling `PARALLAX_PILOT_ENABLED=on` in staging, verify real onboarding, two-account authorization, worker/member revocation, proxy session reload/sign-out, SSE reconnection, and App-authenticated draft publication/reconciliation. Real container persistence now passes locally; live staging and successful Linux execution remain unverified.
